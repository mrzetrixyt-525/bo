Node system

The local node uses the local LXC CLI. Dynamic nodes use node-agent.py.

On a remote node:

sudo apt update
sudo apt install -y python3
sudo mkdir -p /opt/rgnodes-node-agent
sudo cp node-agent.py /opt/rgnodes-node-agent/node-agent.py
sudo chmod 0755 /opt/rgnodes-node-agent/node-agent.py

Install and run the agent as a managed service (the installer generates a strong key when one is not already present):

sudo bash install_node_agent.sh
sudo systemctl status rgnodes-node-agent --no-pager

For a manually started agent:

sudo /usr/bin/python3 /opt/rgnodes-node-agent/node-agent.py --api_key='YOUR_GENERATED_KEY' --host=0.0.0.0 --port=18443

The compatible endpoints are /api/ping, /api/get_host_stats, /api/get_container_stats, and /api/execute.
The agent accepts the key by X-API-Key or Authorization: Bearer ...; query-string API keys are intentionally disabled so credentials do not leak into URLs/logging.
Restrict the agent port with a firewall/private network where possible because the API uses HTTP unless you place it behind TLS.

Multi-node deployment

Admin workflow:

-node create
-node list
-node status <id>
-node check <id>
-node edit <id>
-node regen-key <id>
-node delete <id> [force]

For every remote node, install node-agent.py with install_node_agent.sh, keep the generated API key in /etc/rgnodes/node-agent.env, and expose the agent port only over a trusted/private network or protected TLS reverse proxy. The bot sends the API key in X-API-Key; it is not placed in the URL. Node keys generated by the bot are 64-character hexadecimal secrets.

-deploy uses a paginated node selector, so more than 25 nodes can be used without truncating the deployment menu. Each VPS stores its assigned node_id; lifecycle commands, stats, SSHX, and forwarding execute against that node.

Install / repair

Run as root on the LXD host:

sudo bash setup_rgnodes.sh

The installer is non-interactive and repairs missing packages/configuration. It preserves an existing .env and vps.db. Node.js 20 is not used as the fallback target; the setup prefers Node.js 24.x LTS in 2026.

It checks/installs, as available:

Python 3, pip, venv/dev tooling

build-essential, libffi-dev, pkg-config

OpenSSH server/client

curl, certificates, git, unzip and common network/process tools

QEMU/KVM + libvirt packages when repositories expose them

snapd/LXD when the LXD CLI is unavailable

Node.js 24.x LTS (or a newer installed major) + PM2 for process supervision

davey, PyNaCl, and all dependencies in requirements.txt

LXD storage behavior

If LXD is not initialized and /dev/loop-control is unavailable, the setup uses a deterministic LXD preseed with dir storage instead of relying on automatic loop-backed storage selection. Existing initialized LXD configuration is preserved.

24/7 process model

Only one Discord bot process is allowed.

systemd
  └── pm2-runtime
        └── Python bot.py

A process lock inside bot.py and the setup lock prevent duplicate bot gateway sessions / concurrent setup runs.

Security / stability

SSH configuration uses an sshd_config.d drop-in and validates sshd -t before reload/restart.

LXC command execution does not use shell=True on the host.

VPS names are sanitized before LXC use.

Persistent port forwards are reconstructed after restart and use host-bound LXD proxy devices.

DB writes use SQLite WAL, full synchronization and an application lock.

Deployment/reinstall/clone paths install the guest baseline and anti-mining guard.

A background repair task rechecks running managed VPS for missing baseline guest commands and restores them when needed.

Anti-mining protection is best-effort signature/process detection; it is not a guarantee against a custom/renamed miner and should be combined with host/provider network controls for stronger enforcement.

Configuration

Copy .env.example to .env and set at least:

DISCORD_TOKEN=YOUR_DISCORD_BOT_TOKEN
YOUR_SERVER_IP=YOUR_REACHABLE_HOST_IP

For public port forwarding, do not leave YOUR_SERVER_IP=127.0.0.1.
